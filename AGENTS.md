# AGENTS.md

vchord is a PostgreSQL extension for vector search, written in Rust on pgrx. It provides two index access methods on pgvector's types: `vchordrq` (IVF lists with RaBitQ codes and a rerank) and `vchordg` (graph). Supported PostgreSQL majors, architectures and toolchain versions are in `README.md` and `Cargo.toml`; read them there instead of assuming.

## Layout

- `crates/`: PostgreSQL-free Rust. `vchordrq` and `vchordg` hold the index algorithms (build, insert, search, rerank, maintain, on-disk tuples); `index` holds the page, prefetch and fetch abstractions; `simd`, `rabitq`, `distance`, `vector`, `k_means` are the kernels. These crates have unit tests and run under miri.
- `src/`: the pgrx side. `src/index/vchordrq/am` and `src/index/vchordg/am` are the access method callbacks (cost estimate, scan, build, vacuum); `scanners/` turns scan keys into a search; `gucs.rs` defines settings; `hook.rs` holds planner and executor hooks; `fetcher.rs` reads table rows for rerank and filters.
- `sql/install/` and `sql/upgrade/`: checked-in SQL for each version. `src/sql/` is the bootstrap around the generated schema.
- `tests/`: SQLLogicTest files (`general`, `vchordrq`, `vchordg`; `vchordrq/pg17` needs PostgreSQL 17 or later). `devtools/`: recovery, recorder, symbol and upgrade checks.
- `docs/release-notes/<version>.md`: one entry per user-visible change.

## Build and check

```bash
PG_CONFIG=/path/to/pg_config make build          # the extension builds only through xtask
PG_CONFIG=/path/to/pg_config make clippy
cargo test --locked --workspace --exclude vchord
cargo clippy --locked --workspace --exclude vchord
cargo fmt --check -- --config-path /dev/null --config imports_granularity=Module
taplo fmt --check
sqllogictest --db "$USER" --user "$USER" --label pg18 './tests/general/*.slt' './tests/vchordg/*.slt' './tests/vchordrq/*.slt' './tests/vchordrq/pg17/*.slt'
```

The SQL tests need a running server with `vchord` in `shared_preload_libraries` and the extension installed from the checked-in SQL. Pass the server's major as the label.

The `Check` workflow runs style, lint and the Linux SQL suites on every pull request. Other jobs are opt-in through a `job: +name` line in the pull request body or commit message: `miri`, `check_arch` (other architectures), `simd_emu` (AVX-512 and SVE under emulation), `psql_macos`, `psql_windows`, `psql_alpine`. Ask for the ones your change can break.

When you report a change as checked, say which of these ran, on which PostgreSQL majors and on which architecture. A local x86_64 run is not "CI passes".

## What breaks outside a local run

- New SQL objects need the install script for the current version and an upgrade script from the previous one; `devtools/check-upgrade.sh` compares the two routes. A schema generated by pgrx hides a missing entry.
- Rows at near-equal distances come back in a different order on aarch64 than on x86_64. Do not put near-ties in expected test output.
- Code used by only some architectures needs a `cfg` for them; CI builds with warnings as errors, including on the other architectures.
- Unit tests must be cheap under miri (guard or shrink large cases as the existing tests do), must not leak, and must not compare bits of `powi`-style results.
- A callback PostgreSQL calls is `#[pgrx::pg_guard] unsafe extern "C-unwind"`. A call into a PostgreSQL function pointer goes through `pg_guard_ffi_boundary`. `src/index/hook.rs` shows both.
- Version differences are `#[cfg(feature = "pgNN")]` in Rust and `skipif pgNN` / `onlyif pgNN` in tests.
- Every source file starts with the license header.
- The on-disk format has a version (`crates/vchordrq/src/tuples.rs`). A change to what is stored needs a new version, a statement of which binaries read which indexes, and a release note. `pg_upgrade` carries index files over unchanged.

## Design rules

1. **The index exists to skip work.** The work of a scan should follow the rows it returns, not the rows that exist. `LIMIT`, a sphere radius and a filter key are there to bound lists read, rows reranked and table rows fetched. A change that makes a scan's cost grow with the table or with a filter's row count, by default, needs a maintainer's explicit decision.
2. **Approximate by design.** Recall, the order of near-equal rows and short pages under a selective filter are properties to measure and document. Do not remove one by reading everything unless that is the decision in rule 1.
3. **Changes to defaults and to the scan, rerank, build or cost paths come with numbers.** Old against new, on real embeddings, across filter selectivities, limits and both rerank layouts: lists read, rows reranked, blocks per relation, instructions, recall. Synthetic data is for correctness tests only.
4. **Counts first, then timings, then the cause.** Counts are what the design determines. A timing difference is reported with its cause from a profile, not from arithmetic on medians. Say what was measured and what was read from source.
5. **One implementation.** Judge a change by the final state of the code, not the size of the diff. When a feature needs a variant of an existing path, restructure so both share it; refactoring is welcome. No parallel copies, no parameters appended to long signatures: group them in a type. `#[inline]` and `#[inline(always)]` on hot paths are fine.
6. **No defensive machinery.** An input no real workload produces gets a documented limit or a check outside the hot path. For every guard, state its cost in the work the feature saves. No setting for behaviour that is always better.
7. **A general extension.** Do not bake one application's limits (one key column, a fixed width, equality only) into the format or the interface.
8. **PostgreSQL's own semantics.** Prefer what the planner and executor already provide (quals, rechecks, plan choice) to a private mechanism, and price the scan honestly in `amcostestimate` so the planner can choose.

## Code style

- Idiomatic Rust where it costs nothing at run time. Closed vocabularies are enums, matched exhaustively; no strings standing in for them.
- Comments: one line or none. Say why the code exists when the code cannot; never what it does. No measurements, device names or version-specific numbers in comments.
- Tests: few, at the level of behaviour, deterministic on every supported architecture.
- User-visible text (setting descriptions, error messages, release notes) describes what the code does now. Update it in the same change.

## Commits and releases

- One-line commit subject. No generated-by or co-author trailers.
- Add the release-note entry with the change.
- Do not push, tag, publish a release or change a default on your own initiative; a maintainer decides those.
